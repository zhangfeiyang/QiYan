# 自研 NNUE 数据与特征格式

> 局面轨迹由本项目生成器产生。标签默认来自本项目引擎，也可以显式启用外部
> UCI 教师；当前蒸馏流程使用“学生走棋、Pikafish 只评分”的 DAgger 口径。
> 生成目录中的 `generation-<seed>.properties` 必须随数据保留，用于记录教师、
> 教师网络、学生网络的 SHA-256 和搜索参数。外部教师不随 App 分发。

## 一、特征编码 (Kotlin 与 Python 必须逐位一致)

象棋 90 个交叉点, 14 种棋子(红黑各 7 种)。

棋子索引 `pieceIdx`(0..13), 顺序**固定**, 改动即作废已有数据:

| idx | 子 | idx | 子 |
|----:|----|----:|----|
| 0 | 帅 K | 7 | 将 k |
| 1 | 仕 A | 8 | 士 a |
| 2 | 相 B | 9 | 象 b |
| 3 | 马 N | 10 | 马 n |
| 4 | 车 R | 11 | 车 r |
| 5 | 炮 C | 12 | 炮 c |
| 6 | 兵 P | 13 | 卒 p |

格子索引 `sq = row * 9 + col`, `row 0` = 黑方底线(与 Position 内部约定一致)。

将位桶 `bucket = (kingRow - 7) * 3 + (kingCol - 3)`，范围 0..8；这里的将位
已经变换到当前视角，必在己方九宫。一个桶有 `14 * 90 = 1260` 个特征。

**单视角特征下标**:
`featIdx = bucket * 1260 + pieceIdx * 90 + sq`，取值范围 0..11339。

### 双视角

NNUE 用两个累加器: 走子方视角 + 对方视角。对方视角要把棋盘上下翻转
**并且红黑互换**, 这样网络学到的是"我方/敌方"而不是"红方/黑方", 参数利用率翻倍。

- 我方视角: 先找走子方的将位桶，再编码原视角棋子。
- 敌方视角: 翻转棋盘并交换颜色，按对方将翻转后的格子选择另一个桶。
  - `flipSquare(sq) = (9 - row) * 9 + col`   (只翻行, 列不动)
  - `flipColor`: 红↔黑 同名子互换, 即 `idx` 在 0..6 与 7..13 之间加减 7

## 二、网络结构

```
输入 own[11340] opp[11340]        稀疏, 每边最多 32 个 1
        │          │
   FeatureTransformer (共享权重 11340→256)
        │          │
      acc_own    acc_opp     各 256 维
        └────┬─────┘
          concat 512
             │
      按剩余子力选择阶段桶
             │
      512 → 32 → 32 → 1  →  厘兵分 (centipawn)
          两个隐藏层均为 ClippedReLU
```

共享 FeatureTransformer 是关键: 同一套权重同时服务两个视角, 参数量减半且
天然获得"红黑对称"的先验。

发布基线使用一个稠密输出栈（v3）。实验格式 v4 共享同一个 FeatureTransformer，
但提供 4 个阶段专用的 `512 → 32 → 32 → 1` 输出栈；每个局面只执行其中一个，
因此推理乘加量不变，只增加约 55 KiB 权重。

阶段值由盘面剩余子力计算：将/兵为 0，士/象为 1，马/炮为 2，车为 4，初始
局面合计 40。当前 DAgger 数据分位数对应的四桶为 `0..17`、`18..25`、
`26..35`、`36..40`。阶段只取决于棋子种类，与红黑和走子方无关。

## 三、样本文件格式 (`.bin`, 小端)

每条样本定长 **72 字节**:

| 偏移 | 类型 | 含义 |
|---:|---|---|
| 0 | u8 | `count` 棋盘上棋子数 (最多 32) |
| 1 | u8 | `sideToMove` 0=红 1=黑 |
| 2 | i16 | `score` 走子方视角的厘兵分, 已截断到 ±10000 |
| 4 | u8[64] | `count` 个 `(pieceIdx, sq)` 对, 每对 2 字节; 余下补 0 |
| 68 | i16 | `depth` 打这个标签时的搜索深度 |
| 70 | u8[2] | 保留, 置 0 |

定长是为了让训练侧能 `np.fromfile` 直接 reshape, 不必逐条解析。

`depth` 表示**标签教师**的深度，不是轨迹演员的深度。2026-08-02 之前生成的
外部教师数据曾错误写入本地演员深度 6；旧记录的该字段不能用来筛 d8/d10/d12，
应以原目录/生成日志为准。新数据由生成清单和该字段双重记录。

## 四、标签约定

- **分数始终是走子方视角**(正 = 走子方占优), 与引擎内部 negamax 约定一致。
- 截断到 ±10000: 杀棋分数(±30000 量级)会把回归目标的尺度带偏, 统一压到边界。
- 训练时**网络直接输出厘兵分**, `tanh(·/800)` 放在损失函数里对预测和标签
  两边同时施加。早先的写法是在 dataset 里就把标签变成 `tanh(score/400)`,
  那等于让网络预测 tanh 空间的值, 端上还得做 `atanh` 才能还原, 又贵又在
  ±1 附近数值爆炸。尺度 800 是量出来的: 76k 样本 |分数| 中位数 301、
  90 分位 1295, 饱和率(|tanh|>0.99) 在 400/600/800/1000 下分别是
  12.7%/6.2%/2.5%/1.5%, 而 ±10000 的杀棋分带来 1.3% 的不可约下限。

## 五、量化网络文件格式 (`.nnue`, 小端)

由 `nnue/export.py` 写出, 端上 `NnueNetwork.load` 读入。

v3 文件头为 32 字节，v4 文件头为 36 字节：

| 偏移 | 类型 | 含义 |
|---:|---|---|
| 0 | char[4] | magic `"XQNN"` |
| 4 | i32 | 版本：3=单输出栈，4=四阶段输出栈 |
| 8 | i32 | `FEATURES` = 11340 |
| 12 | i32 | `L1` = 256 |
| 16 | i32 | `L2` = 32 |
| 20 | i32 | `L3` = 32 |
| 24 | i32 | `QA` = 127 (激活值尺度) |
| 28 | i32 | `QW` = 256 (权重尺度) |
| 32 | i32 | 仅 v4：`phaseBuckets` = 4 |

令 `B=1`（v3）或 `B=4`（v4）。紧接着是权重，全部行主序，顺序固定：

| 张量 | 类型 | 元素数 |
|---|---|---:|
| `ft.weight` | i16 | 11340 × 256 |
| `ft_bias` | i16 | 256 |
| `fc1.weight` | i8 | B × 32 × 512 |
| `fc1.bias` | i32 | B × 32 |
| `fc2.weight` | i8 | B × 32 × 32 |
| `fc2.bias` | i32 | B × 32 |
| `out.weight` | **i32** | B × 32 |
| `out.bias` | i32 | B |

v4 的各层都按阶段桶优先排列，例如先连续写 4 个 `fc1.weight`，再写 4 个
`fc1.bias`。加载器继续支持 v3；把 v3 checkpoint 初始化成 v4 时，旧输出栈
会等值复制到四个桶，确保训练起点没有随机结构差异。

结构写进文件头是为了让端上**加载时就拒绝**不匹配的文件。尺寸错位不会崩溃,
只会让网络输出垃圾分数而引擎照样下棋 —— 那种问题几乎查不出来。

### 尺度约定

```
累加器 / 各层激活值   尺度 QA      (1.0 ↔ 127), clamp 到 [0, QA]
权重                 尺度 QW      (1.0 ↔ 256)
乘积                 尺度 QA*QW   除以 QW 回到 QA
输出层               不 clamp, 除以 QA*QW 才是厘兵分
```

除法一律**截断向零** (Kotlin 的 `/`, Python 侧用 `np.fix` 对齐)。向下取整
会在负数上差 1 —— 隐藏层因为紧接着 clamp 到 0 看不出来, 输出层会直接差一分。

### 为什么输出层是 i32 而不是 i8/i16

它要从 32 个 [0,1] 的激活值凑出 ±2000 厘兵的评估值, 权重量级必然在 100 上下;
i8 配 QW=256 只能表示 |w| ≤ 0.496, 差两个数量级。这个坑在没练好的网络上看不出来
(权重全是 0.2 量级, 怎么量化都不截断), 要用 `export.py --stress` 把输出层
放大到真实量级才逼得出来。当前输出层改用 i32，只比 i16 多 64 字节，同时
避免成熟网络的输出权重在导出时饱和。

`fc1`/`fc2` 是 i8, 上限 |w| ≤ 127/256 = 0.496, 靠 `train.py` 每步之后钳位保证 ——
等导出时才发现权重跑到 5 了, 只能截断, 那几天训练就白费了。

### 跨语言一致性

`nnue/make_golden.py` 拿真实自对弈局面跑 Python 参考实现 `int_infer`, 把结果
钉成 `app/src/test/resources/nnue/golden.txt`; `NnueEvaluatorTest` 逐条比对
**完全相等**。整数推理是确定性的, 差一分就说明哪里对不上, 没有"误差范围"可言。

## 六、后悔值着法对格式（实验训练数据）

`mine_regret_pairs.py` 从既有 DAgger 局面中抽样，让当前学生按最终验收的固定
用时（`--student-movetime`）给出着法，再让
PikaFish 分别搜索全局最佳着和由 `searchmoves` 强制的学生着。只有教师分差
达到阈值的局面才写入。该数据只用于训练，不随 App 分发。

每对固定 **144 字节**，直接拼接两个现有的 72 字节记录：

| 偏移 | 长度 | 含义 |
|---:|---:|---|
| 0 | 72 | 教师优选着执行后的子局面 |
| 72 | 72 | 学生着执行后的子局面 |

PikaFish 返回的是根局面走子方视角分数；执行一步后轮到对手，因此写入子局面
前必须翻号。若两个记录的标签分别为 `preferred_y` 和 `rejected_y`，则
`rejected_y - preferred_y` 应严格大于 0，并且正好等于根局面上的教师后悔值。
训练同时约束两个子局面的绝对 value 和这个成对分差，不增加端上网络结构或
推理开销。

每个输出还伴随：

- `.config.json`：源分片、学生/教师二进制和网络哈希、深度、阈值、seed；
- `.progress.jsonl`：每个抽样局面的结果。配对数据先落盘并 `fsync`，再提交
  journal；`--resume` 会据此截掉未提交尾部，避免断电后重复或错位。
